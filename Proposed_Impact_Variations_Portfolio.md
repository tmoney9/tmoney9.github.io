## Pattern Overview

- **Option A (Outcome & Scale-Led):** Leads directly with the primary quantitative metric or scale impact.
- **Option B (Problem-to-Solution Transformation):** Frames the technical bottleneck and how your design system/architecture solved it.
- **Option C (Direct Systems-Architect Voice):** Concise, 1-line lead followed by 3 punchy bullet points detailing architecture, execution, and team alignment.

## 1. Design Tokens for Amazon

### Option A: Outcome & Scale-Led
> Rescued Amazon’s core design token architecture under tight deadlines to support 150+ designers and 300+ product teams building internal employee tools.
> 
> - **Platform release unblocked:** Stabilised the foundational token layer ahead of Amazon’s major September release, preventing multi-team delays.
> - **Multi-mode architecture:** Redesigned the token model to support dark mode, dense views, and future white-label theming.
> - **Engineering alignment:** Audited legacy token failures and established a clean naming convention shared between design and code.

### Option B: Problem-to-Solution Transformation
> Audited and rebuilt Amazon’s flawed design token model under time pressure, turning a risky dependency into a stable foundation for 300+ internal engineering teams.
> 
> - **Systemic audit & fix:** Identified structural failures in the early token model and corrected the architecture before platform rollout.
> - **Future-proofed token model:** Defined clear semantic naming for colour, typography, and spacing to support theming and dark modes.
> - **Governance & hand-off:** Documented token usage rules and led cross-functional reviews to get design and engineering in sync.

### Option C: Direct Systems-Architect Voice
> Led the diagnosis, redesign, and delivery of Amazon’s internal design token system for employee-facing services.
> 
> - **Scaled across 300+ teams:** Standardised token structures used by 150+ designers across HR, pay, and internal portals.
> - **Redesigned token naming:** Replaced rigid hex values with functional, semantic tokens for theming and density controls.
> - **Fixed delivery bottlenecks:** Resolved technical debt in the legacy token setup to meet a strict mid-September deadline.

## 2. SaaS Design Framework (Pipedrive Detail View)

### Option A: Outcome & Scale-Led

> - **Cross-tribe alignment:** Facilitated design reviews across tribes to unify UI behaviours across deal, contact, and organization objects.
> - **Developer-ready library:** Partnered with 5 engineers and a PM to build, document, and release reusable React components.

### Option B: Problem-to-Solution Transformation
> Inherited an undocumented, stalled redesign of Pipedrive's core detail screen and stabilised it into a scalable design framework for new product lines.
> 
> - **Framework over static pages:** Shifted the codebase away from hard-coded views to a reusable framework supporting any CRM object type.
> - **Grounded in user research:** Ran interviews and surveys with internal and external users to target major workflow friction points.
> - **Documented for scale:** Created detailed Confluence guides and design system documentation to speed up team adoption.

### Option C: Direct Systems-Architect Voice
> Led the end-to-end design and delivery of Pipedrive’s object framework, turning a fragile legacy screen into a system for future product lines.
> 
> - **105,000+ active users:** Redesigned the core deal and contact detail screens to eliminate UX inconsistencies.
> - **Reduced technical debt:** Merged isolated team components into a shared framework library aligned with the main design system.
> - **Stabilised team hand-off:** Established clear component specs and shared guidelines between design, product, and engineering.

## 3. SaaS Design System (Pipedrive DS)

### Option A: Outcome & Scale-Led
> Transformed Pipedrive’s legacy Sketch library of 15 poorly structured components into a mature, token-driven Figma system managed as an internal product.
> 
> - **Legacy to modern Figma setup:** Rebuilt component libraries with auto-layout, variants, and semantic tokens for colour and typography.
> - **Centralised System Health:** Built a tracking dashboard monitoring component status across Figma readiness, docs, and code coverage.
> - **Team workflow JIRA setup:** Designed the design ops JIRA space and contribution model to manage backlog priorities predictably.

### Option B: Problem-to-Solution Transformation
> Replaced a VPN-restricted documentation site and broken 15-component library with a modern design system used across all product teams.
> 
> - **Figma & token overhaul:** Restructured components to reduce variant clutter (e.g. rationalising 862 button variants into clean types).
> - **Standardised docs framework:** Created usage, anatomy, behaviour, and accessibility guides directly inside Figma where designers work.
> - **Shared team ownership:** Introduced backlog voting for designers and aligned leadership around a long-term system roadmap.

### Option C: Direct Systems-Architect Voice
> Co-led the end-to-end evolution of Pipedrive’s design system, treating the library as an internal product with dedicated user support.
> 
> - **Tokenized architecture:** Replaced hard-coded hex values with semantic tokens for colour, spacing, radius, and elevation.
> - **CRM pattern templates:** Merged modules and layouts into practical CRM templates (dashboards, tables, forms) for faster workflows.
> - **Leadership alignment:** Worked with product owners and design directors to embed system adoption into the company product vision.

> - **Customer-backed research:** Partnered with Customer Support and non-customer interviews to fix daily navigation pain points.

### Option C: Direct Systems-Architect Voice
> Took full ownership of redesigning Pipedrive’s platform architecture on behalf of the Design Systems team.
> 
> - **End-to-end design ownership:** Led the process from early problem definition to interactive prototype testing.

> - **Multi-app hierarchy:** Structured navigation paths to support new CRM modules without overwhelming first-time users.

## 6. Design System for E-gov

### Option A: Outcome & Scale-Led
> Built a centralised government design system from scratch as the sole designer, unifying inconsistent interfaces across multiple independent departments.
> 
> - **WCAG accessibility first:** Built WCAG-compliant colour palettes and 8px grid layouts tailored for non-tech-savvy civil service workers.
> - **Pattern & form templates:** Standardised Z-pattern form layouts and complex data tables with fixed headers, filters, and row actions.
> - **Organization-wide adoption:** Conducted lectures and created living Confluence documentation to embed UX culture across non-design teams.

### Option B: Problem-to-Solution Transformation
> Overcame departmental silos and rigid government contracting cycles to establish a single, accessible design language for public sector tools.
> 
> - **Zero-to-one system lifecycle:** Owned foundational units, grid systems, component states, and usage guidelines as the sole designer.
> - **Internal user research:** Interviewed analysts, developers, and PMs to tailor components to real operational requirements.
> - **Accessible for under-pressure users:** Designed high-contrast swatches and clear labels for users over 35 working under pressure.

### Option C: Direct Systems-Architect Voice
> Founded and evangelized an enterprise e-government design system across decentralized software development teams.
> 
> - **8px grid & 12-column layout:** Established core typography, spacing, and structural layout rules for desktop tools.
> - **Complex table & form UI:** Created reusable templates for heavy data entry, column searching, and keyboard navigation.
> - **Confluence documentation:** Documented component states, tone, and guidelines in a living hub to streamline developer hand-off.
